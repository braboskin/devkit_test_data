# План T-0D6BFC5A — Чат: meta истории и выбор модели

## Контекст

В `T-78AFCD0D` «Глубокий анализ» отдаётся фронту только в SSE-событии `start`
(`meta.deep`), а `MessageOut` не содержит `meta` — поэтому метка видна у
стримящегося ответа, но пропадает в истории. Владелец также просит настройку
модели из списка доступных прямо в окне чата (как в DeepSeek Chat). Обе вещи
требуют одного: сохранять `meta` у сообщения и принимать `model` в запросе.

Вложения в этой задаче не трогаются: по решению владельца они загружаются из
файловой системы и реализуются в `T-12FFB688` через существующий
`POST /api/documents`; агент при необходимости сам берёт документы приложения.

## Шаги

1. **БД и миграция.** Колонка `meta` (JSON, nullable, default `{}`) у `messages`;
   alembic-миграция с backfill `{}` для существующих строк; PostgreSQL и SQLite
   проверяются тестами схемы.
2. **Схемы.** `MessageOut.meta: dict[str, Any]`; `MessageIn.model: str | None`
   (опционально, обратная совместимость); `meta` в создаваемом сообщении
   ассистента заполняется при генерации: `{"deep": bool, "model": str}`.
3. **Сервис.** `model` из `MessageIn` валидируется по списку моделей провайдера
   (существующий эндпоинт списка моделей; кэш в памяти процесса, TTL ~10 мин):
   неизвестная модель → 422 с понятным текстом; при отсутствии ключа/списка —
   принимается `agent.model` по умолчанию. Выбранная модель уходит в вызов
   провайдера и сохраняется в `meta` ответа. `deep` продолжает работать как
   раньше (топ-K ×2 + инструкция).
4. **Фронтенд.** В композере — `SelectField` «Модель» (значения из
   `/api/settings/llm/models`, fallback — модель агента), выбранное значение
   уходит как `model`; при смене чата восстанавливается модель из последнего
   сообщения (`meta.model`) или модель агента. В ленте у ответа показываются
   метки «Глубокий анализ» и модель из `meta` (и для истории после перезагрузки).
5. **Тесты.** `tests/test_agent_chat.py`: meta сохраняется и возвращается в
   истории; неизвестная модель → 422; валидная — попадает в вызов провайдера и
   `meta`. `tests/test_isolation.py`: поля `model`/`meta` в матрице тел, чужой
   чат по-прежнему 404. E2E: выбор модели → тело запроса содержит `model`,
   после перезагрузки у ответа видны метки «Глубокий анализ» и модель.
6. **Доступность:** у селекта модели есть label; метки — текст, не только цвет.

## Acceptance

- После перезагрузки у ответа в истории видны «Глубокий анализ» и модель.
- В окне чата есть выбор модели; невалидная модель отклоняется сервером (422),
  валидная реально используется в запросе к провайдеру.
- Существующие чаты без `meta` открываются без ошибок (backfill/совместимость).
- Профиль зелёный, e2e обновлён, axe 0.

## Риски

1. Миграция на живой БД: `meta` добавляется nullable — безопасно, но прогнать
   `alembic upgrade` на копии продакшн-схемы (SQLite и PostgreSQL).
2. Список моделей требует рабочего ключа: без ключа валидация невозможна —
   падать в `agent.model`, не блокируя отправку.
3. `meta` растёт со временем: хранить только `{deep, model}`, не цитаты и не
   usage.
4. Выбор модели может конфликтовать с моделью агента — приоритет у явного
   выбора пользователя, в UI подпись «по умолчанию: …».
5. Порядок: задача идёт **после** `T-12FFB688` (общий файл `Chat.tsx`).
