# M4: напоминания и push

Черновик плана M4. Эпик E-46E212B4, ТЗ `TZ-52EEACD7` v0.8, M1–M3 выпущены
(`main` @ `2540bc5`), зависимость `T-B317AFAE` выполнена. Старт кода — после
регистрации версии плана и approve владельцем.

**v4 (replan, 22.11):** исправлен расчёт вхождения для повторяющихся
событий в S3 — серия анкорится от `start_at`. В v3 формула
`pm.next_occurrence(rrule, now - remind - 1s)` задавала `dtstart=after` и
теряла серию: `fire_at` уезжал на период вперёд, AB4 не выполнялся для
`FREQ=DAILY;remind=15`. Требования, scope и acceptance не меняются — это
техническая правка в рамках AB4.

**v5 (replan, 22.11, после независимого ревью):** три блокера и две
major-находки. B1/B2 — планировщик сравнивал UTC с настенным временем из
UI (`datetime-local` пишется naive как есть), напоминания сдвигались на
UTC-смещение, тихие часы/лимит считались в UTC; теперь одно правило:
naive = локальное настенное время сервера, планировщик берёт
`datetime.now()`. B3 — для RRULE окно 60 мин не работало (2*remind) и
`remind_minutes=0` почти не срабатывал; вхождение выбирается по окну
`[now-60м, now]`. M1/M2 — валидация ключей/endpoint подписки и гонка
upsert. SQLite/PG-тест downgrade 0006 на PG не покрыт — уточнено в
отчёте. Scope и acceptance не расширяются; добавляются AB16/AB17.

**v6 (replan, 22.11, после повторного аудита):** N3 — для RRULE берётся не
самое раннее, а последнее должное вхождение (`rule.before(now+remind+1s)` с
нижней границей `now+remind-60м`): для периодов < 60 мин напоминания
систематически опаздывали на 30–60 мин. N1 — на границе доверия aware-время
приводится к локальному настенному (`astimezone().replace(tzinfo=None)`),
иначе `+03:00`/`Z` из API/агента уезжало на смещение. N2 — `read_at` в одной
шкале с `created_at`. N4 — строгий base64url (`validate=True`) и
`ip.is_global` (CGNAT/reserved). N5 — стоимость `rrule` от `dtstart`
зафиксирована как риск R15. Добавлены S11 и AB18; в S4 исправлен `utcnow()`.

**S3. Ядро напоминаний.** Новый `app/backend/reminders.py`: функция
`dispatch_due(db, now, sender=push.send) -> int`:

- события (`remind_minutes is not null`): без rrule `fire_at = start_at -
  remind`; с rrule — серия анкорится от `start_at`: `rule =
  rrulestr(event.rrule, dtstart=event.start_at)`; берётся последнее должное
  вхождение: `upper = now + remind`, `occurrence = rule.before(upper + 1s,
  inc=False)`, пропуск, если `occurrence is None` или `occurrence < upper -
  60м`; `fire_at = occurrence - remind`. Тогда срабатывают поздний скан,
  `remind_minutes=0` и периоды < 60 мин (`FREQ=MINUTELY;INTERVAL=15/30`) без
  отставания на период. `pm.next_occurrence(rrule, after)` для напоминаний не
  годится: он подставляет `dtstart=after` и теряет серию;
- задачи: `due_at is not null`, `status not in pm.CLOSED_STATUSES`,
  `fire_at = due_at`;
- отбор: `fire_at <= now <= fire_at + 60 мин`, иначе пропуск;
- INSERT уведомления: `kind='reminder'`, `title`, `body`, `link='/'`,
  `dedupe_key = f"event:{id}:{fire_at.isoformat()}"` /
  `f"task:{id}:{due_at.isoformat()}"`; конфликт unique → пропуск
  (идемпотентность);
- `reminders_enabled == false` → ничего не создаётся;
- тихие часы (окно, в т.ч. через полночь): уведомление создаётся, push не
  отправляется (`pushed_at` null);
- лимит `max_push_per_day` (count `pushed_at` за локальные сутки) → push
  пропускается, in-app остаётся;
- push после коммита INSERT: `sent` → `pushed_at`; `gone` → удалить подписку;
  `failed` → лог, подписка на месте (дедуп не даст дубль уведомления).

*Результат:* функция тестируется напрямую с `now` и фиктивным sender, без
сети и потоков.

### Откат

1. **Мгновенно:** `ATLAS_REMINDER_SCAN_SEC=0` + рестарт API — новые напоминания
   не создаются, API и данные целы.
2. **Код:** revert коммитов M4 в `devkit/T-9F5FB3D3` (или возврат на `main`) и
   пересборка `viewer` (`npm run build`). SW обновится сам (кэш
   `atlas-shell-v1`); обработчики `push` без серверной отправки не мешают.
3. **БД:** `alembic downgrade 0005_agent_calls` удаляет `notifications`,
   `push_subscriptions`, `notification_settings` — история ленты и настройки
   теряются. Перед откатом после реальной эксплуатации — `pg_dump` /
   `devkit backup` и согласие владельца.
4. **Подписки:** после downgrade сервер не шлёт, `pushManager` в браузере
   остаётся — пользователь отписывается в настройках браузера; отдельная
   очистка не нужна.
5. **Проверка после отката:** `unit-tests` без `tests.test_push` (вернуть
   строку профиля), `/api/notifications` → 404, `devkit task check` на новом
   sha.
