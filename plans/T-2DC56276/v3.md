# M5 v3: развитие, предзаполнение онбординга и общий контекст агентов

## Контекст

План v3 заменяет `v2` и `v1` (оба draft, не утверждены). Отличие от v2 —
исключён бэкфилл legacy-профиля: релиза ещё не было, пользователи
пересоздаются, мигрировать нечего. Остальные решения и структура v2
сохранены. Версии v1/v2 не редактируются.

**Факты на 2026-11-23 (проверено по коду):**

- Эпик `E-46E212B4`, ТЗ `TZ-52EEACD7` v0.8. Все задачи эпика `shipped`, кроме
  M5. `origin/main` = `0ee2bdc` (merge PR #6, `T-0E358820`); локальный `main`
  отстаёт (`824a023`) — база M5 только `origin/main`.
- Head миграций — `0007_job_priority`; M5 создаёт `0008_growth`.
- Кода M5 нет: нет `app/backend/growth/`, моделей `Goal/Habit/Metric/
  JournalEntry/Review`, роутеров, `tests/test_growth.py`, вкладки «Развитие»,
  офлайн-данных.
- Контракт M4: `Notification`, `NotificationSettings`, `push.send`, TTL
  уведомлений, `ATLAS_TIMEZONE` + `config.now_local()/to_wall()`, allowlist
  push-хостов. Тихие часы и дневной лимит — приватные `_in_quiet_hours`/`_push`
  в `reminders.py`; третий потребитель должен переиспользовать, а не копировать.
- Онбординг (`agent/onboarding.py`, `pages/Onboarding.tsx`): 15 фиксированных
  тем, ответы складываются в `user_profile.data["answers"]` и `summary`; ничего
  не создаётся в `spheres/projects/people/goals/habits`. Агент видит только
  `profile.summary`.
- Агент (`agent/context.py`): system message = инструкция + summary + список
  разрешённых сфер/проектов + правила. Данных о целях/привычках/сегодня нет;
  `list_goals`/`propose_create_goal` — заглушка в `tools.py`; `list_events`
  использует `utcnow()` при локальной шкале времени.
- Первый вход сейчас: сразу блокирующий онбординг; LLM-ключ и Яндекс.Диск — в
  «Настройках», провайдера как понятия нет (`base_url` + `model` текстом).

**Решения владельца (2026-11-23), которые фиксирует v3:**

1. Первый вход: провайдер → модель из списка провайдера → apiKey → Яндекс.Диск
   (пропускаемо) → онбординг → приложение.
2. Онбординг — диалог, а не сухая анкета: структурированные вопросы по
   сущностям + свободный шаг «расскажи о себе».
3. Порядок: сначала сферы, потом **для каждой сферы отдельно** проекты
   (автопривязка к сфере). Люди создаются сразу.
4. Сущности создаются **сразу по ходу ответов**; данные онбординга отдельно не
   хранятся (сессия — временное рабочее состояние, после завершения чистится).
5. Общий контекст доступен всем агентам: названия сфер/проектов, цели,
   привычки (включая вредные), метрики, сводка. Содержимое вне scope
   раскрывается по запросу с подтверждением пользователя.
6. Дневник: основной агент («Универсальный помощник») видит полностью; другие
   агенты — частично, по ключам-темам и после запроса.
7. Все изменения — внутри M5 (одна задача, XL по факту; карточка L не
   редактируется CLI 0.1.0).
8. Релиза ещё не было: пользователи пересоздаются; бэкфилл legacy-профиля
   **не входит** в задачу.

**Цель:** пользователь ведёт цели, привычки, метрики и дневник; онбординг сразу
заполняет сферы/проекты/людей/цели/привычки; агенты получают общий контекст и
уточняют детали; по расписанию приходят утренний обзор, недельный отчёт и
проактивные карточки; офлайн-PWA показывает последние документы/чаты; открытые
хвосты M1–M4 закрыты. Acceptance: A7, A8, A12; FR-2, FR-6, FR-10, FR-11, FR-13,
A13, A14 (в уточнённой формулировке).

**Допущения v3:**

1. Обзоры детерминированные, без обязательного LLM; LLM-обогащение текста —
   позже (`ponytail:` в `growth/review.py`).
2. «По запросу раскрываем содержимое» = карточка-предложение `request_access`:
   агент просит доступ к сфере/проекту/теме дневника, пользователь применяет,
   доступ выдаётся на 24 ч и пишется в audit. По умолчанию A14 не ослабляется:
   `search`/`list_documents`/`get_document` видят только `allowed_*` + гранты.
3. Общий контекст не содержит текста документов и дневника; только названия,
   цели, привычки, метрики, счётчики и темы дневника.
4. Основной агент = «Универсальный помощник» (`presets.DEFAULT_AGENT_NAME`);
   признак — новый флаг `agents.journal_access` (true у него, управляется в
   конструкторе).
5. Каталог провайдеров — статический список на клиенте (DeepSeek, OpenAI,
   OpenRouter, «другой OpenAI-совместимый»); в БД по-прежнему только
   `base_url`+`model`+ключ. Новых зависимостей нет.
6. Время — локальное настенное `config.now_local()/to_wall()`, как в M4.
7. Сессия онбординга хранит ответы только до завершения (нужно для «прервать и
   продолжить», A2); после `finish` ответы и состояние чистятся, остаются
   созданные сущности + `user_profile` с предпочтениями и сводкой.
8. Бэкфилл не входит: релиза не было, аккаунты пересоздаются; legacy-профилей
   и данных, которые нужно мигрировать, нет.
