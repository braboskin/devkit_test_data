# T-46BE9A0F — Сканы только на воркере: явная очередь и сообщения (без серверного OCR)

Черновик плана v1, редакция 2026-11-23. Задача `T-46BE9A0F`
(feature/M, эпик `E-46E212B4`); зависимость `T-CA6FF8E2` выпущена,
M4 `T-9F5FB3D3` влита в `main`. Черновик фиксирует решения владельца от
2026-11-22: серверный OCR (tesseract) на VPS **не разрешён**; сканы и
изображения обрабатывает только доступная машина (воркер ПК); при её
недоступности UI явно сообщает, что файл сохранён и обработается позже, без
отмены и без «вечного молчащего queued». Дополнительно — ручное поднятие
документа в очереди (LIFO) и показ в «Заданиях», какой файл обрабатывается.

## Контекст

- На момент проверки `main@1baa23f`; M4 влита, `alembic heads` —
  `0006_notifications`. Отдельный worktree не нужен: текущий checkout
  `repo/atlas` чистый и стоит на `main`. В `main` текстовые PDF до 200 стр /
  50 МБ обрабатываются inline (`T-CA6FF8E2`); изображения, PDF без текстового
  слоя и сверхбольшие PDF уходят в `queued` и ждут воркер ПК
  (`knowledge/pipeline.should_defer`).
- В карточке указано «200 стр / 100 МБ», фактический дефолт
  `ATLAS_PDF_INLINE_MAX_BYTES` — 50 МБ. Для этой задачи лимит не меняем;
  расхождение фиксируем в отчёте.
- Решение владельца 2026-11-22: серверного OCR не будет (tesseract на VPS не
  разрешён). Значит, ветка acceptance карточки «скан становится ready на
  сервере в рамках лимита» **снимается**; остаётся «UI явно объясняет, что
  нужно и почему (без вечного queued)» плюс управление очередью.
- Что уже есть и переиспользуется: `POST /api/worker/claim` (single-flight,
  lease, reclaim), `GET|POST /api/settings/worker-status|worker-token` с
  `last_seen_at` (обновляется на каждом claim, включая пустой), `GET /api/jobs`
  (+ отмена), `_active_job` и `get_owned_or_404` в `documents.py`, UI
  «Документы» с опросом `queued/processing` каждые 5 с, UI «Задания» с
  очередью и блоком воркера.
- Пробелы, которые закрывает задача:
  1. «Документы» не используют `last_seen_at`: пользователь не видит, на
     связи ли воркер и почему скан ждёт; сообщение не объясняет, что файл
     сохранён и обработка не отменена.
  2. Нет способа обработать нужный скан раньше остальных: claim берёт строго
     по `created_at`.
  3. «Задания» показывают «документ #id», а не название, и не показывают
     явно, какой файл обрабатывается сейчас.
  4. На VPS без tesseract быстрый путь текстового PDF с пустой/малотекстовой
     страницей вызывает OCR и падает (`extract_pdf` уже принимает `ocr`, но
     `extract_file`/`analyze_file` его не пробрасывают): `FileNotFoundError`
     → `failed` + 500, оригинал удаляется (`_upload_file`). Inline-PDF должен
     работать без OCR.
- Ограничения: VPS 4 ГБ, новых зависимостей и фоновых обработчиков нет;
  браузерного E2E в проекте нет (принятое ограничение, ручной чек).
- Тулинг: карточку задачи отредактировать нельзя (нет формы/команды), поэтому
  расширение scope на UI и `tests/test_knowledge.py` (согласовано владельцем)
  фиксируется этим планом и отчётом, а не карточкой.

**1. Приоритет задания в очереди (LIFO).**
- `app/backend/models.py`: `Job.prioritized_at: Mapped[datetime | None]`
  (DateTime, nullable).
- `alembic/versions/0007_job_priority.py`: аддитивный `add_column` +
  `downgrade` (`drop_column`); данные/индексы не меняются.
- `app/backend/routers/worker.py`, `claim`: порядок выдачи
  `Job.prioritized_at.is_(None), Job.prioritized_at.desc(), Job.created_at,
  Job.id` (одинаково для SQLite и PG; non-null приоритеты идут первыми, среди
  них — последний поднятый). Single-flight `~running`, атомарный
  `UPDATE ... WHERE status='queued'`, fencing по `attempts` и reclaim не
  меняются.
- `app/backend/routers/jobs.py`, `list_jobs`: при `status=queued` — тот же
  порядок (пользователь видит очередь так же, как её берёт воркер); для
  остальных фильтров — прежний `created_at desc, id desc`.
- `app/backend/routers/documents.py`: `POST /api/documents/{id}/prioritize`:
  404 на чужой документ; активное задание ищем существующим `_active_job`;
  409, если задания нет или оно не `queued` («в очереди нет задания» /
  «документ уже обрабатывается»). Запись — атомарный
  `UPDATE jobs SET prioritized_at=utcnow() WHERE id=? AND owner_id=?
  AND status='queued'`; `rowcount=0` → 409 (задание уже захвачено claim'ом).
  Иначе commit, ответ `DocumentOut`. Повторный вызов обновляет время
  (LIFO: последний поднятый — следующий). Новую job не создавать, статус
  документа не менять, текущую обработку не отменять.
- Поведение: несколько поднятых обрабатываются в обратном порядке поднятия,
  затем остальные по `created_at`; после reclaim протухшее `running`-задание
  возвращается в очередь с сохранённым приоритетом.

**2. Inline-PDF без серверного OCR.**
- `app/backend/knowledge/extract.py`: `extract_file(..., ocr: bool = True)`;
  для PDF передаёт флаг в уже существующий `extract_pdf(path, ocr=ocr)`;
  для изображений при `ocr=False` возвращает пустой текст/`needs_review` с
  причиной `ocr disabled on server` без вызова tesseract (защита, если
  изображение когда-нибудь попадёт в быстрый путь). `extract_image` и
  `scripts/*` не трогаем.
- `app/backend/knowledge/pipeline.py`: `analyze_file(..., ocr: bool = True)`
  передаёт флаг в `extract_file`; `documents._run_fast` вызывает
  `analyze_file(..., ocr=False)` — серверный быстрый путь никогда не
  запускает tesseract. Воркер ПК продолжает вызывать `extract_file` с
  `ocr=True` — его поведение не меняется.
- `should_defer` не меняется: изображения и PDF без текстового слоя
  по-прежнему уходят в `queued`; серверного OCR нет.
- Результат: текстовый PDF с пустой/малотекстовой страницей на VPS без
  tesseract загружается (`ready`/`needs_review` по объёму текста), без 500
  и без удаления оригинала.

**3. Backend-тесты.**
- `tests/test_documents.py`: `prioritize` своего `queued`-документа → 200,
  `job.prioritized_at` заполнен, новой job нет, документ остался `queued`;
  повторный вызов меняет `prioritized_at`; для `processing`/`ready`/`failed`
  и без задания → 409; чужой документ → 404; изоляция (B не поднимает A);
  если задание уже `running`, `prioritize` → 409 и `prioritized_at` пуст
  (атомарный `UPDATE`); загрузка текстового PDF с пустой страницей при
  недоступном tesseract (`mock` `extract.tesseract_binary` →
  `FileNotFoundError`) → не 500, статус `ready`, оригинал на месте.
- `tests/test_ingest_acceptance.py`: очередь LIFO — загрузить A, B, C;
  поднять B, затем C → claim берёт C, потом B, потом A (каждое задание
  завершать/отменять, иначе single-flight не даст следующий claim);
  `GET /api/jobs?status=queued` отдаёт тот же порядок; существующие сценарии
  scan→queued→worker→ready и отмены не меняются.
- `tests/test_knowledge.py`: `analyze_file(..., ocr=False)` на скан-PDF не
  вызывает tesseract (mock `run_tesseract`, assert not called) и возвращает
  текст с текстовых страниц; `extract_file(image, ocr=False)` не вызывает
  tesseract и даёт `needs_review`; `should_defer` для изображения/скана
  остаётся `defer` (регресс политики).

**4. UI.**
- `viewer/src/api.ts`: тип `WorkerStatusInfo { configured: boolean;
  last_seen_at: string | null }` и helper `workerConnection(info, now)` →
  `not_configured | never_connected | offline | online` с порогом 10 минут
  (одна константа). `last_seen_at` пишется сервером в UTC (`utcnow`),
  поэтому при сравнении парсить как UTC (добавлять `Z`); битая дата —
  `offline`. Остальные naive-времена UI не переводим.
- `viewer/src/pages/Documents.tsx`: запросить `/api/settings/worker-status`;
  обновлять его тем же 5-секундным опросом, пока есть `queued/processing`
  (иначе статус воркера застынет). В баннере `queued/processing` показывать
  состояние воркера (не настроен / ещё не подключался / нет связи >10 минут /
  на связи) и текст: файл сохранён на сервере или в Яндекс.Диске, обработка
  не отменена, начнётся/продолжится, когда ПК подключится; ссылка на
  «Задания». У `queued`-документа — кнопка «Обработать следующим» (в списке
  и в карточке) → `POST /api/documents/{id}/prioritize`; после успеха заметка
  «Документ будет обработан следующим». 409/404 — человеческий текст, без
  потери документа. Для `processing` — «обрабатывается сейчас на ПК», без
  кнопки.
- `viewer/src/pages/Jobs.tsx`: подтянуть `/api/documents` для названий;
  показывать «Сейчас обрабатывается: <название>» (job `running`) и очередь
  `/api/jobs?status=queued` в порядке обработки с пометкой «следующий»;
  в блоке воркера — то же сообщение `workerConnection` (worker-token уже
  отдаёт `configured`/`last_seen_at`). `web-build` (tsc + vite) должен
  пройти.
