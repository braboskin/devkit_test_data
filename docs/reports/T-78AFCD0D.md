# Отчёт T-78AFCD0D — Чат: поиск, «Стоп», «Глубокий анализ», вложения

## Что сделано

Четыре функции чата, которые в первом проходе дизайна остались за рамками,
реализованы и покрыты тестами; попутно найден и устранён дефект e2e-инфраструктуры.

**Поиск по диалогам.** Поле в шапке списка (`searchbox`, label «Поиск по
диалогам»), фильтр по названию без учёта регистра и `ё/е` («елка» находит «Ёлка и
ёж»), счётчик «Найдено: N из M» в `role="status"`, пустой результат —
`EmptyState` «Ничего не найдено», `Escape` очищает поиск и не сбрасывает
выбранный чат.

**«Стоп».** Во время стрима в композере вместо «Отправить» — кнопка «Стоп»:
сначала обрывается клиентский `fetch` через `AbortController`, затем вызывается
существующий `POST /api/chats/{id}/messages/{mid}/cancel` с `message_id` из
первого SSE-события. После отмены композер доступен сразу, история
перезагружается, статус отменённого сообщения подписан «Остановлено». Ошибка
отмены не блокирует следующую отправку.

**«Глубокий анализ».** `SwitchField` в композере («Глубокий анализ»), значение
уходит в `MessageIn.deep`. На бэкенде при `deep=true`: в system prompt
добавляется `DEEP_INSTRUCTION` («разбирай альтернативы и ограничения, отвечай
подробно»), tool `search` без явного `limit` получает 10 вместо 5; в SSE
`start` добавлено `meta: {deep: true}`. Модель и провайдер не меняются. В ленте
у стримящегося ответа показывается метка «Глубокий анализ».

**Вложения.** Кнопка-скрепка открывает панель «Документы для контекста»
(`SelectField mode="multiple"`, `GET /api/documents?limit=50`), выбранные
документы — чипы с удалением, лимит 10 (лишнее отсекается), отправка передаёт
`document_ids`. Бэкенд проверяет владельца до записи сообщений: чужой или
несуществующий документ → **422** (приоритетнее 409 «нет ключа»), дубликаты
схлопываются, порядок сохраняется; фрагменты выбранных документов подмешиваются
в контекст с приоритетом выше обычного поиска (бюджет 2400 символов, 800 на
документ, 4 фрагмента).

**Найденный дефект e2e (инфраструктура).** Новые тесты падали на собранном
`dist` (в `dev` проходили): production-сборка регистрирует service worker, а он
перехватывает `fetch` в обход `page.route` — моки `/api/**` не применялись, чат
получал пустой список. В `playwright.config.ts` добавлено
`serviceWorkers: 'block'` (с комментарием): e2e гоняется детерминированно.

## Риски

1. **Семантика `deep`** — тот же провайдер, больше контекста + инструкция
   (утверждено владельцем). Если нужна другая модель — отдельная правка.
2. **Явный `limit` от модели** не удваивается: `deep` меняет только дефолт.
3. **Вложения ограничены владельцем**, не scope агента; если нужно 422 для
   документов вне `allowed_spheres/projects` — продуктовое решение.
4. **Бюджет вложений** — эвристика по символам (2400/800/4 фрагмента), длинные
   чанки могут обрезаться.
5. **Отмена in-memory** (`chat._cancelled`): после рестарта сервера старая отмена
   не сработает (как и было до задачи).
6. **Метка «Глубокий анализ» в истории** появится только если бэкенд начнёт
   сохранять `meta.deep` у сообщения — сейчас `MessageOut` не содержит `meta`,
   поэтому метка видна у стримящегося ответа (из `start`) и не видна в истории.
7. **`serviceWorkers: 'block'`** меняет окружение всех e2e: PWA-офлайн-сценарии
   этим набором не покрывались, но при добавлении офлайн-тестов блокировку нужно
   будет снимать локально.
8. **«Стоп» до первого SSE-события**: `message_id` ещё неизвестен — рвётся только
   клиентский поток, серверный cancel не вызывается; при необходимости жёсткого
   стопа нужен id из заголовка ответа.
