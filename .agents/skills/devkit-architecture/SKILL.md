# devkit-architecture — структура и границы

## Когда

Появляются новые слои или фичи; непонятно, «куда положить файл»; агенты
создают `utils/`/`helpers/` вне объявленной структуры; нужен публичный API
слайса; перед ревью надо проверить, что импорты не пересекают границы.
Не для разовой правки — это `devkit-just-do`; не для проектирования с нуля —
это `devkit-task-plan` / `devkit-epic-plan`.

## Инструменты

- `devkit profile show|set|test` — стек, документы и команды проверок профиля;
- `devkit doc show|list` — ADR и описания структуры проекта;
- CLI-проверка импортов, подходящая стеку: для JS/TS — Steiger или
  dependency-cruiser, для Python — import-linter или pytest (по фактической
  раскладке проекта), иной стек — линтер импортов из профиля;
- git (`log`, `diff`), grep/read; graphify (опционально) — карта зависимостей;
  ponytail (опционально) — минимальное решение;
- Полный CLI-набор devkit: `devkit task plan`, `devkit task check`, `devkit task report`, `devkit doc`, `devkit profile`; применяй только относящиеся к навыку.

## Шаги

1. Объяви структуру в проекте, а не в чате: слои/фичи, что можно импортировать
   из каждого, в какую сторону направлены стрелки. Правила хранятся в документе
   проекта (`profile.docs`, `devkit doc show`) и в конфиге arch-проверки;
   профиль задаёт саму команду проверки (`verification`), а не правила слоёв.
2. Выбери CLI-проверку импортов по фактической раскладке проекта. Проверка
   должна читать текущие каталоги, а не воображаемую структуру.
3. **Проверка обязана ловить нарушение на текущей раскладке.** Прогони её на
   заведомо плохом импорте или на существующем нарушении: если линтер
   структуры на плоском `src` даёт 0 ошибок — он без зубов, а не «всё хорошо».
   Исправь конфиг (правила слоёв, alias), не ослабляй проверку.
4. Публичный API — через точку входа слоя/фичи (индексный файл, `__init__`,
   экспорт пакета). Прямые импорты внутрь слайса — запрещены правилом, иначе
   структура расползётся.
5. Оформи arch-проверку командой профиля (`verification`) и предложи
   `required: true`. Обязательность решает владелец, агент только
   подготавливает и проверяет прогон.
6. Правило для агентов проекта: «сначала слой/фича — потом файл; не создавай
   каталоги вне объявленной структуры». Новые общие места (`utils/`,
   `shared/`) — только с явным правилом в профиле/документе, иначе не создавай.

## Промпты субагентов

- `.agents/prompts/architect.md` — проверить границы слоёв/фич и направление
  импортов, предложить правила и arch-команду; не утверждает план за
  владельца.
- `.agents/prompts/skeptic.md` — аудит «проверка без зубов»: ловит ли
  линтер реальное нарушение, нет ли исключений, глушащих всё.
- Промпт роли подставляется в `prompt` вместе со структурой и списком
  существующих импортов; историю чата не передавай.

## Если инструмент недоступен

- graphify нет → построй карту импортов через `grep`/`rg` по путям и чтение
  `git log`; отметь деградацию.
- ponytail нет → правила `devkit-lifecycle`.
- Нет подходящего линтера импортов → проверяй структуру скриптом/правилом
  профиля (запрещённые пути, разрешённые направления) и зафиксируй
  ограничение; не выдавай grep за arch-проверку.
- `devkit profile test` не работает → прогон вручную с записью вывода и exit
  code.
- Нет документа с объявленной структурой → не выдумывай слои; зафиксируй
  вопрос и эскалируй.

## Доказательства

- Объявленная структура: слои/фичи и разрешённые направления (ссылка на
  `devkit.yaml`/документ проекта и commit sha).
- Arch-команда, вывод, exit code; демонстрация, что проверка падает на
  нарушении (заведомо плохой импорт или существующее нарушение).
- Правило для агентов зафиксировано в инструкции проекта.
- Отчёт `docs/reports/<id>.md`: что объявлено, что проверено, что не
  проверено.

## Если не получилось

Линтер не ставится, структура не описана или проверка требует больше правок,
чем было в scope — не расширяй scope молча и не подменяй проверку фиктивной.
Зафиксируй находку и вызови `devkit-team-escalate` с конкретным запросом:
доступ, решение владельца о структуре или `devkit-replan`.
