# devkit-team-sync — сверка перед финалом

## Когда

Перед финальным ответом, сменой статуса, гейтом и выпуском; после сбора
результатов субагентов; при подозрении на дрейф scope. Это не гейт и не
проверка кода — это сверка обещанного и сделанного.

## Инструменты

- `devkit task show|plan|check|gate|report|comment`
- `devkit profile show`, `devkit doc show`
- git (`status`, `diff --stat`, `diff`, `log`), grep/read
- graphify (опционально), ponytail
- Полный CLI-набор devkit: 	ask plan, 	ask check, 	ask gate, 	ask report,
  doc, profile; применяй только относящиеся к навыку.

## Шаги

1. Восстанови три источника:
   - план: версия `plans/<id>/v<N>.md` и его шаги/scope/acceptance;
   - acceptance: требования задачи и отчёта;
   - факт: `git diff <base>..HEAD --stat`, список файлов, коммиты, `git status`.
2. Построй таблицу «пункт → доказательство → статус»:
   - каждый шаг плана: выполнен/нет/отличается;
   - каждый критерий acceptance: проверка/тест/ручная проверка с id;
   - каждый файл diff: входит ли в scope; файлы вне scope — отдельно.
3. Проверь свежесть доказательств: check-события относятся к текущему HEAD и не
   `invalidated`; гейты не `superseded`; отчёт не ссылается на старый коммит.
   Новый коммит после проверок = проверки недействительны.
4. Проверь гигиену: нет незакоммиченных/untracked файлов, нет секретов в diff,
   нет временных файлов, ветка `devkit/<id>`, нет force-push.
5. Зафиксируй расхождения:
   - недоделанный пункт → вернуть в реализацию;
   - лишний файл → убрать или обосновать и провести через `devkit-replan`;
   - отсутствующее доказательство → не считать пункт выполненным.
6. Обнови отчёт/комментарий таблицей sync. Если расхождений нет — это
   доказательство для гейта; если есть — `devkit-team-check` не запускай до
   устранения.

## Промпты субагентов

Обычно не нужны: sync выполняет ведущий агент. Допустимо привлечь
`.agents/prompts/skeptic.md` для проверки таблицы, передав только план, diff и
acceptance, без истории чата.

## Если инструмент недоступен

- graphify нет → таблицу строй по `git diff`/grep/read.
- ponytail нет → правила `devkit-lifecycle` (минимальность diff).
- `devkit task check|gate` недоступны → возьми id и вывод из отчёта; отметь,
  что свежесть подтверждена вручную.
- Нет базового коммита для diff → используй ветку от default branch и явно
  укажи базу; без базы sync не считается выполненным.

## Доказательства

- Таблица sync: план/acceptance/файлы → доказательство → статус.
- `git status --porcelain` (пусто) и `git diff --stat` с базой.
- Id проверок/гейтов и их привязка к HEAD.
- Запись в отчёте о расхождениях и их устранении.

## Если не получилось

Если расхождение нельзя устранить без изменения требований или scope — не
подгоняй acceptance под факт. Остановись, опиши разрыв и вызови
`devkit-team-escalate` (`blocked`) с вариантами: доделать, урезать acceptance,
вынести в отдельную задачу. Финальный ответ без sync запрещён.
