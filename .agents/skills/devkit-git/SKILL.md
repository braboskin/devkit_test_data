# devkit-git — git в проекте devkit

## Когда

Любой коммит, ветка, merge, push, работа с worktree, pull данных, конфликт или
подготовка к выпуску. Применяется вместе с `devkit-lifecycle`.

## Инструменты

- `devkit task show|status|report|comment`, `devkit task ship`
- `devkit project show`, `devkit doctor`
- git (`status`, `diff`, `log`, `branch`, `switch`, `worktree`, `fetch`,
  `merge`, `push`), grep/read, graphify (опционально), ponytail
- Полный CLI-набор devkit: `devkit task plan`, `devkit task check`, `devkit task report`, `devkit doc`, `devkit profile`; применяй только относящиеся к навыку.

## Шаги

1. Определи репозиторий: data-репозиторий (корень проекта) или приложение
   `repo/<name>/`. В data-репозиторий входят `tasks/`, `plans/`, `epics/`,
   `docs/`, `AGENTS.md`, `.agents/`, `devkit.yaml`; `repo/`, `.devkit/`,
   `worktrees/`, `graphify-out/` не коммитятся.
2. Работай в ветке `devkit/<task-id>` от актуальной целевой ветки. Перед
   началом: `git fetch`, `git status`; не начинай поверх чужих незакоммиченных
   изменений. При параллельных задачах используй worktree (`worktrees/`), не
   переключай общий рабочий каталог.
3. Коммить маленькими шагами: `type(scope): краткий смысл`, в теле или конце
   сообщения — id задачи. Один коммит — одна логическая правка. Не коммить
   секреты, `.env`, токены, `node_modules`, артефакты сборки и временные файлы.
4. Не переписывай историю: без `push --force`, `reset --hard` на общих ветках,
   `commit --amend` для уже опубликованных коммитов. Не удаляй ветку с
   невлитой работой. Не обходи хуки (`--no-verify`).
5. Синхронизация: `pull --ff-only`; при конфликте — остановись, разбери
   конфликт вручную, не выбирай «свою сторону» массово. Конфликт в data-файлах
   (`tasks/`, `plans/`) требует сверки с владельцем, если смысл расходится.
6. Push выполняй только для ветки задачи и только когда это разрешено
   (`devkit-task-ship`). Никогда не пуш напрямую в default/protected branch.
   Выпуск и PR — через `devkit task ship`, он фиксирует попытку.
7. После работы: `git status` пуст, ветка содержит только scope задачи, в
   отчёте — commit sha и база diff. Worktree/временные ветки убери, если они
   больше не нужны и не содержат чужой работы.

## Промпты субагентов

Обычно не требуются. Если разбор конфликта делегируется, используй
`.agents/prompts/architect.md` или `.agents/prompts/skeptic.md` с брифом
«только анализ конфликта, без правок и force». Историю чата не передавай.

## Если инструмент недоступен

- git недоступен → остановись: коммиты и доказательства обязательны, работать
  «на файлах без истории» нельзя.
- graphify нет → `git log -S`, `git grep`, `git diff`.
- ponytail нет → правила `devkit-lifecycle`.
- Нет доступа к remote → локальные коммиты сохраняются; отметь, что push не
  выполнен, и передай владельцу; не переписывай историю.
- CLI devkit недоступен → коммить вручную по этим правилам, отметь деградацию.

## Доказательства

- Имя ветки, база diff, commit sha, сообщения коммитов.
- `git status --porcelain` пуст перед сдачей.
- Список файлов diff и подтверждение, что вне scope ничего нет.
- Для data-репозитория — какие файлы закоммичены, что осталось локальным.

## Если не получилось

Конфликт, который нельзя разрешить без изменения смысла данных, — не
разрешай «как получится»: сохрани обе стороны, зафиксируй `blocked` и
эскалируй владельцу с описанием конфликтующих изменений. Не удаляй чужие
коммиты и не делай force-push, чтобы «починить» состояние.
