# devkit-task-plan — план задачи

## Когда

Задача размера M/L, новый функционал, баг с неясной причиной, изменения
данных/auth/безопасности, несколько файлов или слоёв. Для S с очевидным
acceptance используй `devkit-just-do`. Эпик планируется отдельно
(`devkit-epic-plan`).

## Инструменты

- `devkit task show|create|status|plan|comment|report`, `devkit task brief`
- `devkit profile show|test`, `devkit doc list|show|put`, `devkit epic show`
- `devkit task check` (для последующей проверки)
- git, grep/read, graphify (опционально), ponytail
- Полный CLI-набор devkit: `devkit task plan`, `devkit task check`, `devkit task report`, `devkit doc`, `devkit profile`; применяй только относящиеся к навыку.

## Шаги

1. Собери вход: `devkit task show <id> --json`, `tasks/<id>.md`, эпик,
   `docs/` (ТЗ, ADR), `devkit profile show --json`, `AGENTS.md`. Прочитай
   затронутый код и его вызывающих; graphify — для карты зависимостей.
2. Сформулируй цель одним абзацем и проверяемый acceptance (каждое требование →
   наблюдаемый результат/команда). Неизвестные требования — выпиши; задай
   владельцу только блокирующие вопросы (не больше трёх), остальное прими
   разумным default и пометь допущением.
3. Составь план:
   - **Scope** — точные пути/репозитории, которые будут изменены, и явный
     список «не трогать»;
   - **Шаги** — упорядоченные, каждый с ожидаемым результатом;
   - **Проверки** — имена `required`-проверок из профиля + точечные проверки
     acceptance (команды и ожидаемый exit code);
   - **Риски и откат** — обратимость, миграции, совместимость, как откатить;
   - **Зависимости** — другие задачи/эпики/внешние сервисы.
4. Следуй ponytail: минимальный набор изменений; не добавляй абстракции и
   зависимости «на будущее»; если можно stdlib/native — планируй их.
5. Запиши план файлом `plans/<id>/v<N>.md` (первая версия — `v1`) и создай
   версию через `devkit task plan <id> --file <file>`; закоммить в data-репозиторий.
   Не редактируй уже утверждённые версии — только новая версия.
6. Попроси подтверждение владельца: в web (план `draft` → `approved`) или в
   CLI с `--owner`; команду выполняет владелец, не агент. До подтверждения не
   начинай реализацию. Ожидание — опрос `devkit task show
   <id> --json` не чаще раза в 30 секунд, максимум 15 минут; затем остановись
   в `needs_review` с комментарием, не блокируй процесс навсегда.
7. После approval переведи задачу в `planned`/`in_progress` и переходи к
   реализации (solo или `devkit-team-run`). План — контракт; отклонения только
   через `devkit-replan`.

## Промпты субагентов

Для исследования допустимы субагенты с промптами из `.agents/prompts/`:
- `analyst.md` — требования, acceptance, пробелы;
- `architect.md` — варианты решения, файлы, риски, проверки;
- `techwriter.md` — структура ТЗ/плана, если документация — часть задачи.
Содержимое файла роли подставляется в `prompt` субагента вместе с задачей,
scope и acceptance; историю чата не передавай. Автор плана отвечает за
итоговый документ.

## Если инструмент недоступен

- graphify нет → `grep`/`rg`, чтение файлов, `git log -S`, `git grep`; отметь.
- ponytail нет → правила `devkit-lifecycle`.
- `devkit task plan` недоступен → запиши `plans/<id>/v<N>.md` в git и отметь
  деградацию; версию и hash зафиксируй в отчёте.
- Нет подтверждения владельца → не начинай работу; оставь план и комментарий.

## Доказательства

- Файл плана с версией и commit sha; ссылка на approval владельца.
- Маппинг «требование → шаг → проверка»; список допущений и рисков.
- `devkit task show <id> --json` со статусом/версией плана.

## Если не получилось

Если план отклонён или acceptance противоречив — не переписывай старую версию
и не начинай код: зафиксируй причину, задай блокирующий вопрос и при
необходимости вызови `devkit-team-escalate` (`blocked`). После ответа составь
новую версию через `devkit-replan`.
