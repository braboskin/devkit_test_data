# devkit-team-check — независимая проверка

## Когда

Работа сдана в `needs_review`, проверки профиля зелёные, нужна независимая
проверка перед `done` (его ставит владелец) и выпуском. Также после
существенных исправлений в `replan`. Проверяющий не должен быть автором
проверяемого кода.

## Инструменты

- `devkit task show|check|comment|report|brief|status`
- `devkit profile show|test`, `devkit doc show`
- git (`rev-parse`, `diff`, `show`, `log`), grep/read
- graphify (опционально), ponytail
- субагенты DSH: `subagent`, `send_message`, `wait_agent`
- Полный CLI-набор devkit: `devkit task plan`, `devkit task check`, `devkit task report`, `devkit doc`, `devkit profile`; применяй только относящиеся к навыку.

## Шаги

1. Зафиксируй кандидат: commit sha (`git rev-parse HEAD`), ветку, `git status`
   (чисто), id проверок и версию плана. Не проверяй «плавающий» код.
2. Собери пакет проверки: план, acceptance, scope, diff кандидата, вывод
   обязательных проверок, отчёт. Для каждого проверяющего — свой бриф
   (`devkit-team-brief`), без истории чата и без выводов автора.
3. Запусти **независимых** субагентов с промптами:
   - `skeptic.md` — логика, границы, безопасность, обработка ошибок, лишний
     scope/абстракции, покрытие acceptance; ищет, что сломается;
   - `test-engineer.md` — воспроизводит проверки и тесты, пробует негативные
     сценарии, проверяет регрессию и flaky;
   - по потребности `architect.md` — только для архитектурной оценки.
   Автор кода не участвует в проверке. Каждый ребёнок получает только свой бриф.
4. Проверяющие не правят код. Их вывод — находки с `file:line`, серьёзностью,
   воспроизведением и ссылкой на требование/проверку.
5. Сведи находки в отчёт и комментарий к задаче: `file:line`, severity,
   воспроизведение, ссылка на требование, рекомендация (approve / changes).
   Вердикт в devkit не записывается: рекомендация ничего не блокирует.
6. Есть блокирующие находки → комментарий с конкретными пунктами и возврат в
   `devkit-team-run`/`devkit-replan`. Блокирующих нет → сообщи владельцу, что
   задача проверена; `done` ставит он.
7. Приложи в отчёт: кандидата, находки (открытые/закрытые), рекомендацию, что
   не проверено.

## Промпты субагентов

- `.agents/prompts/skeptic.md` — независимый аудит без права писать код;
- `.agents/prompts/test-engineer.md` — воспроизведение и негативные сценарии;
- `.agents/prompts/architect.md` — только архитектурная оценка, не подмена
  проверки скептика.
Содержимое файла роли подставляется в `prompt` субагента вместе с брифом,
diff и acceptance. Запрещено передавать ребёнку историю чата и просить
«подтвердить, что всё хорошо».

## Если инструмент недоступен

- graphify нет → `git diff`, grep/read, `git log -S`; отметь деградацию.
- ponytail нет → правила `devkit-lifecycle` (проверять минимальность diff).
- Нет субагентов → выполни проверку сам по чек-листу скептика и явно укажи,
  что независимость ограничена; владелец решает, достаточно ли этого.
- Владельческое действие (`done`) недоступно → передай находки и рекомендацию
  владельцу и дождись его решения; не ставь `done` через `--owner`.

## Доказательства

- Commit sha кандидата и `git status`.
- Рекомендация по каждому проверяющему (approve / changes) и её обоснование;
  id проверок.
- Находки с `file:line`, severity, воспроизведением; закрытые пункты.
- Явный список того, что осталось непроверенным и почему это допустимо.

## Если не получилось

Не давай `pass` из вежливости или из-за нехватки времени. Если проверяющий не
смог воспроизвести проверку, кандидат не готов: `fail`/`blocked` с причиной.
Если конфликт между ролями не решается фактами — `devkit-team-escalate`, решение
принимает владелец. Рекомендацию не даёт автор кода, и она не отзывается молча.
