# devkit-replan — пересмотр плана

## Когда

- обязательная проверка провалилась или независимая проверка вернула
  блокирующие находки, и нужен другой подход;
- обнаружена ошибка плана (неверная причина бага, пропущенный слой);
- изменились требования/scope или решение владельца;
- задача `blocked` и владелец дал новое направление.

Не используй для мелкой правки в рамках утверждённого плана — это обычная
итерация реализации.

## Инструменты

- `devkit task show|status|plan|comment|report|check|brief`
- `devkit profile show|test`, `devkit doc list|show`
- git (`log`, `diff`, `show`), grep/read, graphify (опционально), ponytail
- Полный CLI-набор devkit: `devkit task plan`, `devkit task check`, `devkit task report`, `devkit doc`, `devkit profile`; применяй только относящиеся к навыку.

## Шаги

1. Собери факты о провале: id и вывод упавших проверок, находки независимой
   проверки, `git log`/`git diff` с момента предыдущего плана. Отдели причину
   от симптома.
2. Проверь исходные допущения плана: какие из них ложны, какое требование
   acceptance не покрыто, какой риск реализовался.
3. Прими решение: исправить план, сузить scope, разбить задачу, вернуть
   прежнее решение с обоснованием. Не начинай писать код до новой версии.
4. Создай **новую** версию `plans/<id>/v<N+1>.md`:
   - что изменилось относительно `v<N>` и почему (diff по смыслу);
   - исправленный root cause и шаги;
   - обновлённые acceptance и проверки (особенно регрессионная проверка);
   - риски/откат, влияние на уже сделанные коммиты.
   Старые версии не редактируются. Зарегистрируй через `devkit task plan`.
5. Если меняются требования/scope/архитектура — снова запроси approval
   владельца. Если правка чисто техническая в рамках acceptance — отметь это
   в комментарии и продолжай по правилам задачи.
6. Переведи задачу в `in_progress`, выполни новый план. После двух провалов
   одной и той же гипотезы — `devkit-team-escalate`, не третья попытка наугад.

## Промпты субагентов

- `.agents/prompts/skeptic.md` — независимый разбор, почему план/проверки
  провалились, без авторства кода;
- `.agents/prompts/architect.md` — альтернативное решение и его цена;
- `.agents/prompts/test-engineer.md` — какая проверка должна была поймать дефект.
Промпт роли подставляется в `prompt` вместе с версией плана, выводом проверок
и scope. Историю чата не передавай.

## Если инструмент недоступен

- graphify нет → `git log -S`, grep/read, чтение diff.
- ponytail нет → правила `devkit-lifecycle`.
- `devkit task plan` недоступен → новый файл версии в git + отметка деградации.
- Нет доступа к выводу проверки → не восстанавливай по памяти: перезапусти
  проверку или запроси лог у владельца.

## Доказательства

- Причина провала со ссылками на id проверок и коммиты.
- Новая версия плана и её commit sha; diff к предыдущей версии.
- Повторный approval, если менялись требования/scope.
- Запись в отчёте: что сработало, что нет, какая проверка теперь ловит дефект.

## Если не получилось

Если после пересмотра причина всё ещё не ясна или требуется решение вне твоих
полномочий — остановись, зафиксируй `blocked` и эскалируй. Не расширяй scope
молча и не отключай проверку, которая мешает. Владелец должен увидеть варианты
и цену каждого.
