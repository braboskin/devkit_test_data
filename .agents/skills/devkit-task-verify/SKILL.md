# devkit-task-verify — прогон и фиксация проверок

## Когда

Реализация задачи закончена (или сделана итерация исправлений), нужно прогнать
обязательные проверки профиля, записать результаты и передать задачу на
независимый гейт. Не используй для финального вердикта — это делает
`devkit-team-check` / владелец.

## Инструменты

- `devkit task show|check|comment|report|status`
- `devkit profile show|test`, `devkit doc show`
- `devkit task gate` — только чтобы увидеть существующие гейты, не ставить свой
- git (`status`, `diff`, `rev-parse`), grep/read, graphify (опционально), ponytail
- Полный CLI-набор devkit: 	ask plan, 	ask check, 	ask gate, 	ask report,
  doc, profile; применяй только относящиеся к навыку.

## Шаги

1. Зафиксируй кандидат: `git status --porcelain` (должно быть пусто или только
   ожидаемые незакоммиченные файлы), `git rev-parse HEAD`, ветка `devkit/<id>`.
   Проверки привязываются к commit sha; новый коммит делает старые проверки
   недействительными.
2. Прочитай `devkit profile show --json`: список `verification` с `name`,
   `required`, `cwd`, `timeoutSec`, командами платформы.
3. Для каждой `required`-проверки и для точечных проверок acceptance выполни
   команду из профиля ровно как записана (тот же `cwd`, без «улучшений»).
   Выполни команду, затем запиши результат:
   `devkit task check <id> --name <check> --status passed|failed|error --output "<вывод>"`.
   Вывод ограничивается лимитом (`checkOutputMaxKb`), хвост ошибки сохраняй.
4. Разбери результат:
   - `ok` — подтверди exit code и что проверка относится к текущему коду;
   - `failed` — классифицируй: дефект задачи, сломанное окружение, flaky.
     Flaky-проверку перезапусти один раз; если снова нестабильна — не считай
     зелёной, зафиксируй и эскалируй.
5. Обнови `docs/reports/<id>.md`: команда, exit code, id проверки, commit sha,
   сокращённый вывод, что не проверено. Не пиши «всё ок» без id.
6. Переведи задачу в `needs_review` и передай на независимый гейт
   (`devkit-team-check`) или владельцу. Вердикт сам не выставляй.

## Промпты субагентов

Для независимого прогона подойдёт `.agents/prompts/test-engineer.md`: субагент
воспроизводит проверки по профилю и возвращает команды/exit code, не меняя
код. Промпт подставляется в `prompt` вместе с профилем и commit sha; историю
чата не передавай. Автор кода не должен сам подтверждать финальный гейт.

## Если инструмент недоступен

- graphify нет → проверки от этого не зависят; используй команды профиля,
  grep/read и `git log` для контекста.
- ponytail нет → правила `devkit-lifecycle`.
- `devkit task check` не подключён → выполни команды вручную, сохрани полный
  вывод с exit code в отчёт и приложи путь к логу; не выдумывай id.
- Профиль `missing`/`invalid` → остановись, сначала `devkit-profile-setup`.
- Нет сети/зависимостей → проверка не считается пройденной; зафиксируй
  `failed`/`blocked`, не подменяй её.

## Доказательства

- Id всех check-событий, имя, exit code, commit sha, длительность.
- Полные команды и `cwd`; хвост вывода для упавших проверок.
- `git status` и HEAD на момент прогона; отчёт `docs/reports/<id>.md`.
- Отдельно: какие `required`-проверки не запустились и почему.

## Если не получилось

Если обязательная проверка падает по причине задачи — верни в реализацию
(`devkit-task-plan`/`devkit-replan`), не снижай требования. Если причина
внешняя (инфраструктура, доступ) — после одной попытки перезапуска зафиксируй
`blocked` и эскалируй. Не помечай `needs_review` с красными обязательными
проверками.
